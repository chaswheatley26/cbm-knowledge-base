# Rewst Webhook Contract

**Current design (2026-07-29, second revision):** two webhooks, async +
poll. This supersedes both earlier designs:
- The *original* spec's 3-webhook design (`submit-url`/`check-status`/
  `list-history`) assumed persisted, browsable submission history — dropped
  because the actual requirement never needed it.
- The *first simplification*'s single synchronous webhook — dropped because
  the full enrichment chain (VirusTotal/URLScan/Safe Browsing/RDAP + a
  Claude verdict call) runs 60-90s in the happy path, too long to reliably
  hold one HTTP request open end-to-end.

What's below is the current, live contract. See `phishing-src/CLAUDE.md` for
the deployed webhook URLs and what's still left on the Cloudflare Worker
side.

---

## 1. `triage` trigger (submit)

Fired by `cloudflare-worker.js`'s `submit` action, fire-and-forget
(`wait_for_results: false`). The Worker generates `request_id` itself
(`crypto.randomUUID()`) and embeds it in the payload — it never parses or
depends on this trigger's immediate response body, only whether the POST
was accepted at all. This sidesteps a documented Rewst platform issue: async
trigger acks can come back completely empty (no execution_id, nothing) even
when the workflow genuinely ran (see the KB tool's `CLAUDE.md` History
#7/#11-13/#17).

**Input:**
```json
{
  "submitted_input": "either a bare URL or a full pasted email, unknown which until classified",
  "submitter": "optional free-text name",
  "client_tenant": "optional free-text client/tenant",
  "request_id": "uuid, generated by the Worker — use this as the key everything else looks up by"
}
```

**Step 1 — classify `submitted_input`:** treat as an **email** if it contains
header-like lines (`From:`, `To:`, `Subject:`, `Received:`, `Reply-To:`) or is
clearly multi-line prose with an embedded link, rather than being just a bare
URL on its own. Otherwise treat as a **bare URL**.

- **Bare URL path:** enrich that one URL only (VirusTotal, URLScan, Safe
  Browsing, RDAP).
- **Email path:** extract every URL found in the body (regex for
  `https?://\S+`) and run the same four-source enrichment on **each** one;
  additionally pass the full raw email text to the Claude verdict step so it
  can reason over email-content phishing signals (sender/display-name
  mismatch, Reply-To spoofing, urgency language, spelling) — not just link
  reputation.

**Step 2 — enrichment, per URL:** explicitly mark any source that failed or
timed out — never leave a field blank or default it to a clean/benign
reading. Suggested per-source shape:
```json
{ "status": "ok", "summary": "5/90 engines flagged" }
{ "status": "failed", "summary": null }
{ "status": "timeout", "summary": null }
```
Known quirk: `safe_browsing.summary` has been observed coming back as a
*nested object* (`{ "status": "ok", "summary": "No threats detected" }`)
instead of a plain string like the other three sources. The frontend
defensively stringifies non-string `summary` values so this can't crash
rendering, but flattening it to a plain string on the Rewst side would
match the other three sources and remove the need for that.

**Step 3 — Claude verdict call.** See `claude-verdict-prompt.md` for the
system prompt/schema. Feed it: all per-URL evidence (with failed/timeout
sources explicitly marked as such, not omitted), plus the raw email text and
`email_signals` extraction when the input was an email.

**Step 4 — store the result, keyed by `request_id`**, transiently — an org
variable named after the request_id, or equivalent. This is **not**
persisted submission history; there's no browsing/listing of past
submissions. `get_result` (below) deletes this after a successful read, so
it doesn't accumulate. Store the same object shape described in step 3 of
`get_result` below.

**Step 5 — side effects**, independent of what the frontend ever sees: post
verdict + screenshot to Teams; `malicious` → create/update an Autotask
ticket; `suspicious` → internal Autotask note only.

## 2. `get_result` trigger (poll)

Fired by `cloudflare-worker.js`'s `poll` action with `wait_for_results:
true` — a fast lookup-and-return, not a long-running job, so the proven
synchronous pattern applies here (unlike `triage`).

**Input:** `{ "request_id": "..." }`

**Output — while still processing (nothing stored yet for this
`request_id`):**
```json
{ "status": "pending" }
```

**Output — once complete:** delete the stored result after reading it, then
return:
```json
{
  "status": "complete",
  "result": {
    "input_type": "url | email",
    "urls": [
      {
        "url": "string",
        "virustotal": { "status": "ok|failed|timeout", "summary": "string|null" },
        "urlscan": { "status": "ok|failed|timeout", "summary": "string|null", "screenshot_url": "string|null" },
        "safe_browsing": { "status": "ok|failed|timeout", "summary": "string|null" },
        "rdap": { "status": "ok|failed|timeout", "summary": "string|null" }
      }
    ],
    "email_signals": {
      "sender_display_name": "string|null",
      "sender_address": "string|null",
      "reply_to_mismatch": true,
      "urgency_language_detected": true,
      "notes": "string"
    },
    "verdict": {
      "verdict": "benign | suspicious | malicious | insufficient_data",
      "confidence": 0,
      "reasoning": "string",
      "recommended_action": "string"
    }
  }
}
```
`email_signals` is present only when `input_type` is `"email"`.

**Note on the exact wrapper key:** the `triage` webhook's response shape has
already changed once during testing (it came back nested under
`final_response` rather than the originally-assumed `verdict` key) — so
`src/lib/api.js`'s `checkStatus()` deliberately checks a few plausible
wrapper keys (`result`, `final_response`, `output`, `data`) rather than
assuming exactly one. If `get_result`'s actual response uses a different
wrapper than `result` shown above, that's fine — no frontend change needed
as long as it's one object containing `verdict`/`input_type`/`urls`. Update
this doc to match whatever it actually is once confirmed live, same as was
done for the synchronous version's contract before this revision.

## Known failure modes to guard against (carried over from the spec)

- Never let a failed/timed-out enrichment source silently read as "clean" —
  `insufficient_data` exists specifically so thin evidence doesn't get
  reported with false confidence.
- VirusTotal free tier: 4 req/min, 500/day. If a submission hits this,
  reflect it in that source's `status`/`summary`, don't silently drop it.
- Both VirusTotal and Google Safe Browsing free tiers are non-commercial-use
  only — CBM is an MSP serving paying clients, which is commercial use.
  Flagged for a licensing decision before any client-facing production use;
  not blocking build/testing.
- **Stale/duplicate poll edge case:** if a poll response is lost in transit
  after `get_result` has already deleted the stored value, a retry of that
  same poll will look identical to "never existed" / permanently pending.
  Low-stakes for a low-volume internal tool; worth a `status: "not_found"`
  distinction later if it ever actually causes confusion.
